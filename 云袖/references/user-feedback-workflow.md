# 用户反馈落实：声画、表演与局部补镜

导演设计、实片反馈回修及续做时读取。具体人物、秒数、素材和授权以项目配置及对应集记录为准；本参考不授权生成或剪辑。

## 1. 先读项目，再确认本次工作范围

- 用户要求查看进度时，读取配置、input、对应output与实际媒体，分别汇报已写稿、已填写、已提交、已生成、已检查及已归档的状态。
- 用户说明自己正在制作某段、稍后提供视频时，记录等待交付；不能将其计划当作成片完成。收到指定视频后检查实际媒体及尾部来确认接续状态，再从实片选取站位／背景连续性关键帧，不继续采用旧稿的假设结尾，也不直接引用原始尾帧生成下一段。
- 后续纠正覆盖同一事项的旧要求，例如“半句后推镜”替代“整句后推镜”；同步权威稿、计划和操作记录。不同集的选择按集保存，不能互相覆盖。

## 2. 旁白先校时，画面逐句对应

- 当前优先保证更多原文旁白念出，不能因画面替代自动删句。用户提供旁白并要求对应时，以实际音频为时间基准，记录每句起止与承载镜头；原件保留，自动对齐与实际试听状态分开记录。
- 按旁白当下所说的事件呈现相关人物、动作或证据。不得用无关反应凑时长，或用“生成时无旁白”省掉必要画面。
- 用户要求快切时，以相邻切点间隔尽量不超过3秒设计；先缩掉无信息等待，再按事件节拍切换。完整对白、关键动作和阅读时间不能硬截；确需长镜时说明依据并遵循项目已确认的例外。
- 推镜是连续运镜，不计作一次切镜。标清推镜从哪半句或哪个词后启动、如何随剩余台词推进，不能把“半句后”写成整句结束后。

## 3. 前段实片、连续性关键帧、表情与屏幕播放层级

- 用户要求“以这个为开头，直接拉镜头”时，先确认“这个”指向的是用户已指定的关键帧及其状态，不得用原始尾帧直接绑定给下一段。仍按站位／背景连续性关键帧分维度引用，并在运动描述中从该状态立即后拉，不先增加停留或重复表演。
- 同步继承人物造型、视线、姿态、表情和光线。没有新刺激，不把冷笑或得意改成惊讶、惊恐。
- 从脸部拉出电脑屏幕时，明确屏幕播放的是过去录像还是当前直播。过去录像中的人物不能回应后来出现的评论或舆论；只改变外部观看层级，不能把人物变形为电脑。
- 用户指定身高差、仰视与情绪意图时，将相对高度和机位落实到站位及具体镜头。仰视是摄影角度，不等同人物抬头；不泛化成所有反派镜头的固定拍法。

## 4. 电脑删帖：区分实体手与界面光标

- 写清电脑、桌面、鼠标和操作手的位置及支撑。实体手握桌面鼠标，屏幕内白色箭头移动到目标按钮；不能把“鼠标移到删除”误写成手移向屏幕。
- 动作顺序为光标移动→悬停→鼠标点击→按钮响应→帖子消失或结果显示。界面文字和结果以剧情需要为限。
- 屏幕大特写可将手和鼠标放在画外，用点击声对应界面响应；不为表现点击加入触屏或手指穿屏动作。

## 5. 局部补镜与用户合并选择

- 收到实片缺陷先定位受影响镜头和前后接点，做局部替换素材；情绪或动作错误应先修复，再考虑增强。
- 用户要求两个补镜一起时，将两项修复放入同一独立空白生成单元，内部按需要分镜，不继续分别提交旧草稿。“两个补镜事件”不强制等于恰好两次连续拍摄。
- 分别记录生成时长、有效使用区间及拟替换原片区间。平台最低时长造成的余量不等同必须保留的剧情，不在本流程执行视频剪辑或拼接。
- 平台默认GPT/Codex内置浏览器、自由模式、自动放入资产，每集独立项目；不重复询问。用户说“先检查”时保留待提交；明确生成且费用授权覆盖后只提交一次。新补镜费用按当前页面确认，历史单次授权不自动扩大为新任务或重试额度。
- 记录真实提交状态、费用和节点。续做先查原任务，不能因等待重复生成；设计已修正不代表成片缺陷已消除。
